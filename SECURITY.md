# Security Policy

SovraiOS is source-available under the Sustainable Use License (see
[LICENSE](LICENSE)). This policy applies to everyone with access to the
repository.

## Reporting a vulnerability

Use the repository's **Security → Report a vulnerability** option when available
to send a private report to the maintainers. Do not include vulnerability details
in public issues, pull requests, logs, or screenshots.

If private reporting is unavailable, contact a maintainer listed in
[CODEOWNERS](.github/CODEOWNERS) through a private contact method on their GitHub
profile. If no private contact is listed, open an issue asking only for a private
security contact, without describing the vulnerability. Repository maintainers
should enable private vulnerability reporting before the public launch.

Include the affected commit, iOS version, desktop version, reproduction steps,
expected impact, and a minimal example with pairing links, secrets, and personal
data removed. Coordinate a fix and disclosure timeline with maintainers; no
response-time guarantee is offered. A vulnerability in the desktop side of phone
control belongs to [SovraHarness](https://github.com/Sovra-AI/SovraHarness/blob/main/SECURITY.md).

## Supported versions

Report issues against current `main`, and identify the commit you tested. No
store release is published yet, and there is no long-term support or backport
policy.

## Handling secrets

- The phone key is 32 random bytes generated by the Rust transport and stored
  with `expo-secure-store` in the iOS Keychain as `AFTER_FIRST_UNLOCK_THIS_DEVICE_ONLY`,
  so it does not leave the device. Android builds of this code disable backup.
- The pairing link is a bearer invitation. It is decoded in memory, sent once
  inside the encrypted channel, and dropped. It is never stored, logged, put in
  navigation state, or left on the clipboard.
- Only public routing hints and a display name are saved after pairing. Corrupt
  saved data fails closed and is treated as unpaired.
- Secrets, keys, and pairing links must never enter repository files, logs, or
  commit history. If one is committed, treat it as compromised: revoke the phone
  in Sovra on the computer, then remove it from history.

## Dependency and build posture

- `iroh` is pinned to the desktop's version, and the wire format is tested
  byte-for-byte against fixtures copied from the desktop.
- Native projects (`ios/`, `android/`) are generated from [app.json](app.json) and
  config plugins and are not committed; neither are built static libraries.
- CI runs type checking, lint, Jest, `cargo test`, and `cargo clippy -D warnings`.

## Data and execution boundaries

The app controls the Sovra window on the paired computer only: it inspects its
controls, presses them, types, and reads the text Sovra labels (messages and
controls), plus screenshots where the desktop provides them. It has no access to the
computer's operating system, files, or shell beyond what Sovra's own window allows.

Traffic uses Iroh QUIC with the desktop's key pinned, directly or through Iroh's
encrypted relays and address lookup, which see connection metadata but not
content. The desktop starts phone access off on every launch and revokes a phone
with **Forget**. Mutations carry a revision from an inspection taken immediately
before, and input whose outcome is unknown is never replayed. See
[Architecture](docs/architecture.md) and the
[desktop contract](https://github.com/Sovra-AI/SovraHarness/blob/main/docs/remote-control.md).
